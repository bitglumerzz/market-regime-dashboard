# Исследовательский отчёт: стек для локального ИИ‑советника (market-regime-dashboard) и платного Telegram‑бота @regime_ai_bot

Дата: 30 сентября 2026. Все факты ниже прошли повторную проверку; там, где первоисточник был недоступен из облака, это явно помечено (раздел 8). Ничто в этом документе не является обещанием доходности: цель стека — честно измерять качество сигналов, а не «гарантировать прогноз».

---

## 1) Кратко

1. **Данные.** Сейчас пайплайн (data_provider.py, cache_5m.py, sentiment.py) видит только цену. Самое дешёвое усиление — позиционирование на перпетуалах (funding, OI, long/short, ликвидации) через ccxt 4.5.84 (MIT, без ключей), Deribit DVOL, Coin Metrics Community (32 дневных on‑chain метрики, бесплатно, CC BY‑NC) и макро (FRED, CFTC, Fear & Greed). Bulk‑историю брать с data.binance.vision, public.bybit.com и okx.com/historical-data, а не через пагинацию REST.
2. **Хранилище.** Parquet (Hive‑партиции, zstd) + DuckDB **1.5.x** (`duckdb>=1.5,<2`). DuckDB 1.4 LTS уходит с поддержки в сентябре 2026, 2.0 — альфа с релизом в конце октября. QuestDB/ClickHouse — только при реальном тиковом потоке.
3. **Модель.** GaussianHMM + Эллиотт + Claude‑судья — это признаки, а не прогнозист. Реальный прогнозист — LightGBM 4.7.0 / CatBoost 1.2.10 на triple‑barrier мета‑метках; второй детектор режимов — statsmodels 0.15 MarkovAutoregression; третий — собственный BOCD (~80 строк).
4. **Валидация.** Только purged/embargo CombinatorialPurgedCV (purgedcv 0.1.8, MIT или skfolio 1.4.9), Deflated Sharpe с честным числом попыток N, PBO. skfolio DSR (PR #255) не смержен; pypbo и backtesting.py — AGPL, в платном сервисе не использовать.
5. **Калибровка.** Conformal‑интервалы (MAPIE 1.5.0 `TimeSeriesRegressor.update`, crepes 0.9.1) + Brier/reliability в prediction_log.py. Бот публикует «P(цель за N баров)=0.58, калибровано на 400 событиях», а не «точность 90%».
6. **Foundation‑модели рядов — только baseline.** Две работы по финансам (arXiv 2511.18578, 2606.27100) дают ~50–51% направленной точности и отрицательный OOS R²; Kronos на 5‑мин BTC неотличим от броуновского движения. Лицензии: Chronos‑2 (Apache‑2.0), TimesFM‑2.5 (Apache‑2.0), Kronos (MIT) — можно; **TimesFM 3.0 и Moirai 2.0 — non‑commercial**, в платном продукте нельзя.
7. **Развёртывание.** Mac (Apple Silicon) = движок под launchd + APScheduler 3.11 (`apscheduler<4`), локальный LLM для русского комментария (Ollama 0.35.x стабильный; MLX‑по‑умолчанию только в 0.40‑rc; mlx‑lm 0.31.3 напрямую). Бот — на Hetzner CX23 (€5.49/мес) вне РФ. Связь Mac→VPS — уже реализованный исходящий HMAC‑push в bot/regime_bot/api.py, без входящих портов на Mac.
8. **Claude‑судья.** Репозиторий на claude-opus-4-7 и anthropic 0.x (>=0.30.0). Планировать миграцию на claude-opus-5-5/claude-sonnet-5-5 (кэш $0.20/MTok чтение, минимум 512 токенов после миграции — на 4.7 всё ещё 2048), Batches −50% (результаты хранятся 29 дней; `fallbacks` в батчах запрещён).
9. **Оплата.** Цифровые подписки внутри бота — **только Telegram Stars** (XTR), `subscription_period=2592000` (ровно 30 дней), ≤10 000 Stars; aiogram 3.31.0 (Bot API 10.3). Это уже реализовано в bot/regime_bot. Второй рельс для карт РФ — Tribute (10%, выплаты в ₽/€), третий — Crypto Pay (USDT/TON). Вывод Stars только в TON через Fragment (~$0.013/Star, холд 21 день — по вторичным источникам).
10. **Юридика и география — главные риски, а не данные.** Telegram в РФ с февраля 2026 троттлится/блокируется (работает через обновлённые клиенты/VPN); 282‑ФЗ о цифровых валютах действует с 01.09.2026; ИИР (39‑ФЗ), 152‑ФЗ, маркировка рекламы, 54‑ФЗ. Нужен юрист до первой продажи; никаких формулировок про гарантированную доходность.

## 4) Как честно мерить качество сигналов

**Что сейчас не так.** GaussianHMM + Эллиотт + Claude‑судья не имеют супервизорной цели, leak‑proof кросс‑валидации и калиброванной неопределённости — поэтому сегодняшний выход нельзя честно продавать как «прогноз».

**Протокол:**

1. **Метки.** Triple‑barrier (±k·σ_GARCH, вертикальный барьер) на событийных барах (новый top‑кандидат волны, флаг HMM/BOCD). Мета‑метка: модель предсказывает P(primary‑направление сбудется), а не направление само.
2. **Разделение данных.** Никакого KFold/TimeSeriesSplit без purge/embargo. CombinatorialPurgedCV: purge ≥ длины вертикального барьера, embargo ~2% выборки. Использовать **только filtered (каузальные)** вероятности режимов — smoothed и in‑sample BIC делают бэктест красивее live.
3. **Walk‑forward.** Обучение на окне → прогноз на следующем блоке → сдвиг; скользящее переобучение по расписанию (идея FreqAI `live_retrain_hours`), но с фиксированными гиперпараметрами, выбранными внутри purged‑CV.
4. **Метрики.** Для классификатора: Brier, log‑loss, reliability‑диаграмма, ECE; empirical coverage conformal‑интервалов (проверять ежемесячно — при смене режима покрытие падает → расширять или abstain). Для «стратегии на сигналах»: expectancy на сделку **после** комиссий (0.05% фьючерсы / 0.10% спот + слиппедж), Sharpe с издержками, PSR, DSR с честным N (все trial'ы optuna + все MLflow‑запуски + все sweep'ы vectorbt), PBO (CSCV) по путям CPCV, minimum track‑record length. Hit‑rate ≠ expectancy: 55% при симметричных барьерах может быть отрицательным.
5. **Гейт на промоушен модели.** DSR > 0.95, PBO < 0.2, expectancy после издержек > 0 на всех тест‑путях; иначе — не в production, что бы ни показывал raw Sharpe.
6. **Baseline‑ы.** Random walk / бутстрап‑Монте‑Карло (monte_carlo.py), Chronos‑2 zero‑shot (только после cutoff предобучения), простые правила. Своя модель обязана бить их после издержек.
7. **Live‑цикл.** Каждый опубликованный прогноз → prediction_log.py с ext_id, p_calibrated, target, invalidation, horizon; verify_predictions() закрывает исход; MAPIE `.update()`; compute_stats() публикует rolling Brier, покрытие, expectancy.
8. **Публичная статистика.** Страница/команда `/stats` в боте: число событий, Brier по горизонтам, reliability‑график, покрытие интервалов, доля abstain, expectancy после комиссий. Без «точность 90%». Честная калибровка требует нескольких сотен закрытых событий на горизонт — это 3–6 месяцев live‑логирования на 4h/1d по нескольким активам **до** того, как за вероятности можно брать деньги.
9. **Аудит судьи.** Выход claude_rescore.py — такой же признак: через тот же purged‑CV/калибровку; трейсы в MLflow 3.
10. **Стресс.** stress_tests.py/sensitivity.py по режимам (BOCD‑границы, ruptures‑разметка), отдельная оценка по каждому историческому режиму, а не только агрегат.

## 5) Оплата и подписки в Telegram — рекомендуемая схема

**Правило №1:** цифровые подписки внутри бота — только Stars. Санкция за фиат/провайдеров — бот и мини‑апп перестают показываться мобильным пользователям.

**Схема:**

```
/start → согласие на ПДн (отдельная кнопка) → дисклеймер → тариф
   ├─ [Stars]   createInvoiceLink(XTR, subscription_period=2592000, ≤10 000 Stars)
   │            pre_checkout (≤10 с) → successful_payment → grant_access(user, 30d)
   │            продление: новый successful_payment(is_recurring=True) → продлить
   │            отмена: editUserStarSubscription(is_canceled=True)
   ├─ [Карта РФ]  ссылка на подписку Tribute → webhook trbt-signature → grant_access(expires_at)
   └─ [Крипта]    Crypto Pay invoice (USDT/TON, fiat-номинал) → webhook paid → grant_access(30d)
grant_access → subscriptions(user_id, source, until, charge_id) → invite-ссылка (member_limit=1) / доступ в личке
APScheduler hourly: истечения → ban/unban в канале, напоминание за 3 дня, /paysupport
```

**Тарифы и цены.** Из‑за ~30–35% потерь на Stars (сторы + Fragment + TON) и 10% у Tribute — цену в Stars выставлять с учётом этого; desktop‑пользователей направлять на покупку Stars через web/Fragment. Квартал/год — разовые инвойсы (рекуррент только 30 дней). Не более одной активной подписки на telegram_id.

**Учёт.** Единая таблица subscriptions с источником платежа и charge_id; сверка getStarTransactions/getMyStarBalance; реестр выплат Tribute; вывод Stars — минимум 1 000, холд 21 день, только TON через Fragment (проверить доступность выплат для вашей юрисдикции). Все webhook‑и — идемпотентны, только с проверенной подписью.

**Надёжность доставки.** Telegram в РФ с февраля 2026 троттлится/блокируется ([Moscow Times](https://www.themoscowtimes.com/2026/02/10/roskomnadzor-tightens-restrictions-on-telegram-as-users-report-disruptions-a91907), [Amnezia](https://amnezia.org/blog/telegram-restricted-in-russia-2026), [Wikipedia](https://en.wikipedia.org/wiki/Blocking_of_Telegram_in_Russia)): массовая блокировка 14–15 марта, ~95% отказов к 10 апреля, обновление клиента 11 апреля восстановило работу для обновлённых приложений. Планировать запасной канал (веб‑страница/email) и не обещать SLA RU‑аудитории. Bot API 10.x добавил ephemeral/rich messages — проверить применимость для персональных уведомлений об истечении.
